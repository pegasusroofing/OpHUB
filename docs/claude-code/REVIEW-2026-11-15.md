## 2. Fixed today: the HR work

Nothing below was ever used against real data: there are no HR records, documents or access settings saved yet.

1. **"Sees" also meant "can change".** Someone you let see a person's Performance could add and delete goals, write private notes, and start or sign off an appraisal. Now seeing is read-only. Only HR and the person's **line manager** (set on their Employment) change those. Private notes are read by HR, the line manager and the writer only.
2. **Switching every part to No still showed the usual parts.** Now saving people with no part is refused, with a message.
3. **Saving one person could quietly switch "company admins see everyone's" on** where an HR team had been named without them. It now stays as it was.
4. **Pressing Save on an admin's pop-up took them off the named list.** That pop-up now has nothing to save and says why they see everyone's.
5. **If the last person who sees everyone's left, nobody could get back in**, and someone changed to a client kept access. Named people must now still be staff, and with nobody left the company admins get back in.
6. **Someone allowed to see a folder also got probation and leaving dates.** Now job title, department and line manager only.
7. **"All Project Managers" (from this morning's first version) couldn't be switched off.** It shows again wherever it's on.
8. **Choosing a parent folder as the HR folder** (say "Live Projects") would hide every project inside it from everyone else. The picker now asks first, in plain words.
9. **Old routes closed.** The first versions' ways of changing who's on the list skipped the "at least one person" check and the change log.

Database record: `sql/hr-review-fixes-15nov.sql`. Proven on the live database: a viewer reads but can't add a goal, sign off an appraisal or read private notes; the line manager can; the old routes refuse; admins get back in when the last HR person goes.

Also fixed: the new app's web pages now send security headers (no framing by other sites, HTTPS only, camera and location for this site only).

## 4. Speed

**Done today**
- **Reads give up after 12 seconds.** On a dead signal a screen could hang for a minute before falling back to its saved copy. Saves, uploads and sign-in are never cut short.
- **The project list opens instantly** from the copy saved on the device, then refreshes behind. It feeds the menu, Home, the Hub and Finance.
- **Less re-fetching.** Projects, Finance settings and the Finance overview are kept for 2–5 minutes instead of 30 seconds. Every save that changes them still refreshes at once.
- **70 database indexes added** on the columns every Finance, HR and Yard read filters on. No difference today; it stops things slowing as invoices grow.

**Bigger jobs, in order of how much faster the app would feel**
1. **The menu's badge reads nine Finance tables** on every app open for Finance users. Count in the database instead.
2. **The first load is about 4 MB** because the PDF builder is loaded up front. Load it only when someone presses Export.
3. **Long lists draw every row** (Sales, Purchases, Materials, Projects). Show 50 and "Show more", or draw only what's on screen.
4. **The Hub makes its requests in six rounds**, one after another. Three could run together: about a second saved on 4G.
5. **Taps wait for the server** (ticking a to-do, check-in). Show the change at once and save behind.
6. **Screens ask for every column** (193 places). Ask only for what's shown, starting with projects.

## 6. How we've been building, and which helpers suit it

**What's working**
- Rules live in the database, not just in the app. That is why the foundations held up.
- Every change gets a screen test, and the tests are kept.
- Database changes are recorded as files, and only add.

**What to change**
1. **Review before "done", not after.** Today's HR work went live on the beta link with ten faults that a reviewer found in six minutes. From now on, anything touching who-sees-what gets the bug reviewer and the security reviewer run in the background before you're told it's finished.
2. **The screen tests can't see permission faults.** They run against a pretend database with no rules. The permission tests I run by hand on the live database (and undo) should be kept as files and re-run before every push.
3. **Shorter sessions.** This one conversation has grown very long. A fresh session per job is cheaper and makes fewer mistakes, because less has to be remembered.
4. **Server functions pasted in by hand** is slow and error-prone. (The 39 that had no copy here were copied in on 15 Nov.) Setting up Supabase's own deploy tool on the laptop would make each deploy one command.
5. **No automatic check on push.** A push goes straight to the live website. A free GitHub check (types and unit tests) would stop a broken push.

**Helpers (agents)**

| Helper | Status | Use it for |
|---|---|---|
| `bug-reviewer` | Have it | After every batch. It found today's HR faults. |
| `andy-ui-checker` | Have it | Before showing you a screen: your layout rules, laptop and phone. |
| `prepush-check` | Have it | Before Push origin. |
| `security-reviewer` | **New today** (`.claude/agents/security-reviewer.md`) | Any change to database rules, server functions, files or sign-in, and before a new company goes live. Proves the rules on the live database with tests that undo themselves. |
| A speed checker | Suggest later | Counts requests per screen in the test harness and flags a screen that got slower. Worth it once the bigger speed jobs are done. |

Use cheaper models for the wide sweeps (speed, searching) and the strongest for security. Three reviewers at once, as today, is the most that's worth paying for.
